1. 整体定位与核心结论

线程归属（2026-11-03） RobotRuntime 与 RuntimeServer 由 KernelHost 托管专用内核循环。状态机和事件总线仍为纯 asyncio； 技能、仓储、状态源、对账和参数校验在固定外部线程执行。SDK 监听在调用方循环消费跨线程 事件快照，异步用户回调不在内核循环执行。超时与取消只有限等待真实停止；未确认动作进入 RECONCILIATION_REQUIRED，资源保持隔离。线程不能强杀，不提供进程隔离或硬实时保证。

这套系统实现了「任务状态变更 → 事件 → 用户回调」的通知能力。它的本质是异步事件流（async event stream），而非经典的观察者（Observer）模式。

核心结论 没有"观察者对象"，也没有"发布者遍历调用回调"。发布者只把事件 put_nowait 进队列就立即返回；真正调用用户回调的，是订阅方自己的协程在消费事件流的过程中执行的那一行 _invoke(...)。回调责任从"发布者"移到了"订阅者"。
维度经典观察者模式本项目实现
订阅者形态观察者对象，持有回调引用一个 asyncio.Queue + 一个监听协程
通知方式发布者遍历观察者，逐个调用发布者入队即返回，不碰回调
谁触发回调发布者（push）事件循环 + 订阅协程自己（pull）
慢订阅者阻塞发布者发布零阻塞；同步回调共享有界线程容量，超载结束对应监听

三个硬约束（详见 第 7 节）是发布者零阻塞、事件可回放、订阅者可控挂起。内核沿用纯 asyncio；SDK 监听层用自管的有界 daemon 线程池隔离同步用户回调，不增加外部依赖。

2. 事件如何诞生：唯一写入点

所有事件只有一个产出点——task_state.py 的 TaskStateStore.transition()（内核不变量 1：任务状态唯一写入点）。它在持有该任务锁的前提下，按固定四步顺序执行：

  1. 快照：深拷贝当前 Task，套用变更得到新快照；
  2. 原子持久化：repository.apply_transition(snapshot, Event(...)) 一次调用同时写入任务快照和事件（序号 = 计数器 + 1）；
  3. 回填：把权威结果逐字段写回活对象，让执行中的代码立即看到新状态；
  4. 最后才发布：self._events.publish(stored_event)。

顺序的意义：publish 在锁内、持久化之后，因此事件的发布顺序严格等于状态迁移顺序，且订阅者读到的事件一定已经落盘。

# task_state.py:104-133（精简）
async def transition(self, task, event_type, changes=None, data=None, guard=None):
    async with self.task_locks[task.id]:
        snapshot = self.snapshot(task)
        if changes:
            snapshot = snapshot.model_copy(update=changes)
        if event_type is not None:
            sequence = self.sequences[task.id] + 1
            persisted, stored_event = await self._repository.apply_transition(
                snapshot, Event(task_id=task.id, sequence=sequence, ...))
            self.sequences[task.id] = sequence
        self.adopt_snapshot(task, persisted)
        if stored_event is not None:
            self._events.publish(stored_event)   # ← 锁内、持久化后发布
        return True

3. EventBus：先回放、后实时、水位去重

历史回放按 event_page_size 分页（默认 128 条），每批之间让出内核循环。 内存与 SQLite 仓储实现可选 PagedEventRepository；旧仓储在外部线程内裁页。 订阅、普通调用与控制操作分别限额，查询、取消和关闭的容量预留会传递到端口线程。

events.py 的 EventBus 是事件的唯一分发组件。它自身不存事件——持久化在 TaskRepository，总线只维护「谁在等」和「发到哪了」。

3.2 subscribe()：三阶段流水

3.3 关键顺序与竞态解法

「先注册队列、再回放」是全局最关键的顺序决定。读仓库是异步 I/O，回放期间内核可能继续 publish 新事件；若先回放再注册，这个窗口内的事件会永久丢失。先注册后，新事件落进队列，由水位（watermark）裁决它是「回放已覆盖」还是「新事件」。

水位去重的两个方向 回放阶段 yield 前抬水位 → 重订阅不重复；实时阶段 sequence <= watermark 直接丢弃 → 回放期间入队的新事件不重复投递。两条防线配合，做到「不丢、不重」。

3.4 背压与关闭

内核关闭先停止业务，再限时清理调用方监听；异步回调吞取消也不能无限阻止关闭。 关闭后事件缓存受 max_event_buffer 限制（默认 1000 条），溢出显式报告 EVENT_STREAM_OVERFLOW 并附最后实际交付的序号，供重新订阅恢复回放。 跨边界快照默认最多 1 MiB、64 层，结果和错误均在工作线程净化后交接。

  • 发布零阻塞：publish 是纯同步函数，put_nowait 即返回，内核状态机永不被订阅者拖住。
  • 背压有界：队列满 1000 触发 _overflow，清空队列并注入一条 EventStreamOverflow（携带当前水位 = 断点续传位置），订阅方抛错后可凭 after_sequence 无损重订。
  • 关闭：close() 置标记并给所有队列 put_nowait(None)，正在 get 的订阅者收到哨兵退出。

4. 回调分发：_observe 状态机

listeners.py 的 TaskListener._observe 是回调分发的核心。它是在 submit_task 返回后，由 _track 用 asyncio.create_task 启动的每任务一个监听协程。

循环体里两个 if self._closed: return 是防御性检查，分别在回调前与回调后——因为回调本身可能耗时，期间监听器可能被 close()。注意 return 与 break 语义不同：return 是「不玩了」整个监听作废，break 是「玩完了」进入结果阶段。

4.1 回调统一入口 _invoke

# 分发示意；完整取消及结果清理见 sdk/listeners.py
async def _invoke(self, callback, *args):
    try:
        if is_async_callback(callback):     # async 函数或 async __call__
            result = callback(*args)
        else:
            result = await executor.submit(callback, *args)
        if inspect.isawaitable(result):
            await result                    # 在所属事件循环等待
    except asyncio.CancelledError as error:
        current = asyncio.current_task()
        if current is not None and current.cancelling():
            raise
        raise ListenerCallbackError("Task callback cancelled itself") from error

异步回调在调用方事件循环执行，普通函数在回调工作线程执行；普通函数返回的 awaitable 回到调用方循环等待。内核线程只提供事件快照，回调还会收到独立的 model_copy(deep=True) 副本。同步回调不能直接操作 asyncio 对象，应改成 async 回调或使用 loop.call_soon_threadsafe。

sdk/callback_executor.py 自管 4 个 daemon 线程和最多 64 个排队项，排队期限 5 秒，不依赖 ThreadPoolExecutor 私有实现或退出钩子。取消监听会撤销未领取工作；已领取工作视为在途，关闭不等待它，完成结果和异常被丢弃。永久阻塞的线程仍占槽位，不会被强制终止或补建。wait() 也不限制运行时长。

4.2 错误上报 _report_error

订阅、查询或回调的任何异常，只结束该任务的监听协程：有 on_error 则调它（传 task_id + 异常）；on_error 缺失或自身再抛，则交 asyncio 事件循环异常处理器，不静默吞错。业务任务与内核状态机零感知。

队列满和排队超时分别上报 LISTENER_CALLBACK_QUEUE_FULL、LISTENER_CALLBACK_TIMEOUT。同步错误回调也受队列约束，失败后交给循环异常处理器；异步错误回调不占工作线程。回调自行抛出的取消映射为 LISTENER_CALLBACK_FAILED，关闭监听触发的取消正常传播。

5. 让出点与唤醒机制

订阅者不轮询。没有事件时，它完全挂起在 await queue.get()，不占用 CPU。这是事件驱动（event-driven）而非轮询（polling）。

轮询本实现
无事件时反复醒来空查冻结在 await queue.get()
CPU 开销有（空转 + 定时器）无
响应延迟≈ 轮询间隔入队后下一个调度点，近乎即时
谁驱动订阅者自己的循环发布者的 put_nowait

5.1 唯一常驻让出点

让出控制权的位置在 events.py:81 的 queued = await queue.get()。更精确地说，是它驱动到的 asyncio.Queue.get 内部 await getter（future 未完成）那一刻。

yield 与 await 的区分（关键） yield（async generator 里）不是让出事件循环，而是「向消费者交一个值」，消费者帧原地继续——这是生成器协议，不是调度。await 未完成的 future 才是把控制权交还事件循环的调度动作。第 81 行是后者，所以是让出点。

5.2 唤醒路径

publish(event)                 # 状态变更时被调用
  queue.put_nowait(event)      # ① 值进队列
                               # ② 同时把挂在 get 上的 future 置完成
                               # ③ 事件循环下一轮恢复订阅协程

asyncio.Queue 内部：get() 队列空时创建 future 存进 _getters 并 await；put_nowait 时有等待中的 getter 就 set_result(值)。所以入队和唤醒是同一次调用完成的，订阅者是被「顶」醒的，不是自己「问」醒的。

7.2 为什么"绕"，是否值得

三个硬约束决定了这套写法：发布者不能阻塞（状态机唯一写入点必须同步返回）、事件可回放（重启后能补发）、订阅者可控挂起（没事件就睡着）。这是纯 asyncio 下解耦生产者/消费者、且要求可回放、可断点续传时，最接近标准答案的写法。

代价是认知门槛高：要求读者同时掌握 async generator、yield/await 的区别、aclosing、协程让出点四件事。但这是理解成本，不是正确性问题。

结论 状态机与事件总线保持纯 asyncio；SDK 使用有界守护线程隔离同步回调。监听可关闭，但在途同步代码的副作用无法强制终止；容量耗尽通过结构化监听错误降级。测试覆盖事件顺序、异常隔离、关闭竞态、队列期限及永久阻塞下的进程退出。
