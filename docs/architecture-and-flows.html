1. 定位与设计目标

robot-agent-runtime 是机器人本机任务执行运行时：接收"一串技能调用"构成的任务， 负责准入、资源互斥、超时、取消、状态持久化、事件推送和重启后的状态核对。

四条设计目标决定了整个架构的形状：

  1. 内核零领域知识。运行时不认识"急停""电量""导航"，只做集合求交 （ports.py:103-126）。 领域模型全在适配器里。这条决定了内核可以长期不换。
  2. 硬件/依赖可替换。内核不 import 任何厂商 SDK、ROS 2 或云 SDK；外部能力一律实现 ports.py 的 Protocol，靠结构匹配注入，不注册、不继承。
  3. 不确定就不重放。物理动作非幂等，所以"数据库里是 RUNNING"不构成继续执行的理由。 这条决定了恢复流程、RECONCILIATION_REQUIRED 状态和 quarantine 的存在。
  4. 内核循环不可被外部代码冻住。厂商 SDK 里的同步阻塞调用不能拖死状态机。 这条决定了 2026-11-03 的线程边界改造（本文第 6 节）。

明确不是目标的：硬实时保证、功能安全（急停必须靠硬件回路）、进程级故障隔离、 并发调度与抢占、重试。见 README.md:606-611。

2.2 线程拓扑

一个用 RobotRuntime + SQLite + 3 个技能 + 状态源 + 对账器的嵌入式进程，全部用默认（独占）绑定时长这样：

线程 谁创建 上面跑什么 数量
主线程（应用 loop） 应用 SDK 门面、TaskListener 协程、异步回调 应用自定
robot-kernel KernelHost hosting/kernel_host.py:183-187 整个 RuntimeCore：状态机、资源锁、事件总线、asyncio.Task 1
robot-extension-shared / robot-extension-group-{name} / robot-extension-dedicated-{i} IsolatedPorts hosting/isolation.py:530-537 归属该线程的全部外部对象方法（技能 execute / 仓储读写 / watch / reconcile） 按绑定分组，≤ 唯一对象数
robot-validation IsolatedPorts hosting/isolation.py:528-529 jsonschema 准入校验（外部可控的 CPU 工作） 1
rar-callback-N CallbackExecutor callback_executor.py:84-86 SDK 的同步监听回调（惰性创建，daemon） 最多 4

远程模式则在服务端进程重复整套拓扑，客户端只是普通应用线程 + UDS。

五条关键规则：

  • 粒度由调用方声明，默认仍是"一个对象一条线程"。注册端口时可以把实现包在 ThreadBinding.shared(...) / .group(obj, name) / .dedicated(...) 里 （thread_binding.py:12-49）， IsolatedPorts 按 (mode, 组名或 id(obj)) 归组、按 id(obj) 去重 （hosting/isolation.py:508-521）。 也就是说：dedicated 以对象身份为键、group 以组名为键、shared 不分名字（所有 shared 对象合成一条）。 同一个实例注册成两个名字仍然只有一条线程；不同对象用不同模式可以共存，但同一个对象给出两种 绑定会在启动任何线程之前以 InvalidRequest 拒绝（hosting/isolation.py:516-517）。 绕开宿主直接用 RuntimeCore(...) 时只接受普通端口对象，并在当前循环执行； 线程绑定与隔离由宿主负责，低层内核不接收或拆包 ThreadBinding。
  • 共享的只有 loop，失败归属仍按对象。同组对象可以做协程式并发，但一个不返回的同步调用会冻结整组； 反过来，对象级故障（毒化、_Skill._poisoned、资源隔离）仍各自独立，同组里一个对象超时不会把邻居一起判死。
  • 状态源不得与可能阻塞的技能同组。需及时交付前置条件变化（急停、掉电）的 RobotStateProvider 一旦和阻塞技能共用 loop，watch() 的标签更新要等技能那个同步调用返回才能发出。 实测（同一实现，技能里塞一个不 yield 的阻塞调用）：独占绑定下急停标签约 206 ms 送达并打断任务， 共享到被阻塞的那条组线程上则 >1000 ms 才送达。配对测试把差别写死：独占时 TASK_PRECONDITION_LOST 一定到达、任务落 RECONCILIATION_REQUIRED，同组时 0.1 s 内一定不到达且任务仍是 RUNNING （test_thread_binding_boundaries.py:154-217）。
  • 线程永不替换：卡住的线程一直占着，不补建 （hosting/thread_runtime.py:75-82）。 这是"无法杀死线程"的直接后果，也是当前设计的主要运维代价。
  • 上限：线程组数 len(keys) + 校验线程 1 不得超过 max_extension_threads（默认 32）， 超出在构造期抛 EXTENSION_CAPACITY_EXCEEDED （hosting/isolation.py:520-526）。 全用默认独占时线程组数就等于外部对象数（仓储 + 技能 + 状态源 + 对账器）；共享/分组只减线程， 不减对象，也不改任何端口契约。

2.3 容量与预留位

每条 LoopThread 有两个独立名额：普通名额 max_pending 和控制名额 control_capacity。 判断依据是 CONTROL_OPERATION 这个 ContextVar （hosting/execution_context.py:4）， 在 _execute 里按 job 设置，因此控制属性会沿调用链传到端口线程 （hosting/thread_runtime.py:205）。

目的只有一个：get_task_status / cancel_task / 生命周期清理不能被 256 个空闲订阅或一堆慢请求挤出去。三档是分别记账的：请求档 max_pending_calls=256、控制档 max_control_calls=16 在 _submit_request 里用两个 set 各自限流（hosting/kernel_host.py:361-374）， 订阅档 max_subscriptions=256 按 self._streams 数量限流 （hosting/kernel_host.py:425-429）。 线程自身的队列容量比这三档更宽：robot-kernel 线程的普通名额是 max_pending_calls + max_subscriptions，控制名额是 max_control_calls + 3 （hosting/kernel_host.py:183-187）， robot-validation 与每条外部线程同样多给 3 个控制位兜底 （hosting/isolation.py:528-536、 理由写在 hosting/isolation.py:490-498）。 这 3 个位子专门留给"公开查询正在等外部代码时"仍要能挤进去的清理调用（如 iterator.aclose()）。 容量耗尽统一报 EXTENSION_CAPACITY_EXCEEDED。

名额挂在线程上，不挂在对象上（限流点在 LoopThread.submit， hosting/thread_runtime.py:117-130）。 所以合并成组除了合并失败半径，还合并了 256 + 19 这套名额：一个组里 10 个对象一起排队时， 挤占的是同一个池子；独占则是每人一份。反过来，这也是"对象太多、fd 吃紧"时共享省下的那部分—— 省的是线程和 fd，不是吞吐预算。

3. 数据模型与状态机

3.1 模型

TaskRequest(task_type, steps[SkillCall], priority, timeout_s, idempotency_key, metadata)
  └─ 落库为 → Task(id, task_type, state, steps, current_step, priority, timeout_s,

要点：

  • SkillDefinition 是声明式的，校验/加锁/超时/取消全由运行时按声明统一执行，技能实现里 不许自己做（AGENTS.md 不变量 6）。
  • TaskRequest.timeout_s 现在是总期限，从接受请求那一刻起算，覆盖准入、排队、等资源、执行 （kernel/core.py:288-289）。
  • SkillContext 里的 cancel_event 是内核的 asyncio.Event，但技能在线程隔离下拿到的 是代理在自己线程里重建的等价 event（hosting/isolation.py:413-424）， 绝不跨线程共享 asyncio 对象。
  • 全部时间戳强制 timezone-aware UTC（_as_utc → UTCDateTime，models.py:70-76）。 技能进度不是 Task 的字段，只以 SKILL_PROGRESS 事件形式存在——状态里没有可被覆盖的 progress，就不存在"进度写入和状态机抢同一个字段"的问题。

流程 2：提交任务（准入）

kernel/core.py:321-402。顺序是有意为之的：

  1. submit_task 先用内核循环的单调时钟算出总期限 deadline（:288-289）， 然后 _submit_owned 包在 asyncio.shield 里——调用方取消不能把已登记的任务变成孤儿， 必须等本机归属登记完才允许逃逸（:290-299）。
  2. idempotency_lock 内查幂等键，命中直接返回既有任务；否则建 Task、create_task 落库、 register() 登记本机归属（:302-321）。
  3. 依次发 TASK_CREATED、TASK_VALIDATING。
  4. 取一次 unsatisfied() 快照，整单所有步骤共用这一份读数（:334）， 然后逐步 validate。隔离模式下校验被派到 robot-validation 线程（:335-336、 hosting/isolation.py:578-599）。
  5. 任何 AgentRuntimeError → 落 FAILED 并 cleanup()，返回任务而不是抛异常（:347-358）。 这是"校验失败也是一次合法的任务生命周期"的体现。
  6. 通过则发 TASK_QUEUED，create_task(executor.run(task, deadline)) 并登记执行句柄。 submit_task 不等执行——它返回的是 QUEUED 快照。

注意：priority 落库了但不参与排序，也没有并发上限，提交即起协程。调度器还没做。

流程 4：取消、超时与"停止确认"

这是整个项目最容易被误读的部分。三层，每层都不能证明物理停止：

第 1 层  cancel_event.set()           协作信号，技能自己轮询/等待
第 2 层  task.cancel()                仅当 supports_cancel=True
第 3 层  停止确认期 cancel_grace_s     等真实结束（默认 0.2s，可再来一轮）
  • cancel_task：取本机任务 → request_cancel（发 TASK_CANCEL_REQUESTED，置状态 CANCELING） → cancel_event.set() → 释放生命周期锁后才 await shield(execution) （kernel/core.py:381-405）。 锁内不做等待，否则取消会把整个内核的提交路径堵死。
  • executor._confirm_stop：等 cancel_grace_s；没结束且 supports_cancel 才 task.cancel() 再等一轮。 判定标准是"任务真的结束且结果可信"：TaskCancelled 或 SkillResult.success 才算确认； 协程 CancelledError、任何异常、返回失败结果都算不确定 → ExecutionUnresponsive （kernel/executor.py:300-328）。
  • 上面还叠了一层：_Skill 代理自己也有 _CancelBridge + _poisoned， 确认不了就永久拒绝该技能实例（hosting/isolation.py:458-488）。
  • 后果链：ExecutionUnresponsive → resources.quarantine(声明的资源) → 任务落 RECONCILIATION_REQUIRED → 迟到结果不得把任务改回成功，终态后不再收进度。
  • 隔离永不自动解除（kernel/resources.py:23-37）。 后续等待者拿到锁后还会再查一次隔离表（kernel/resources.py 里 yield 前的 _require_available）， 所以"软件任务结束了"绝不等于"硬件可以复用了"。

总期限到期走同一套：未派发或已确认停止 → FAILED / TASK_TIMEOUT； 停止不明 → 待对账（kernel/executor.py:160-176）。

流程 5：事件订阅与回放

kernel/events.py + hosting/kernel_host.py 两段，合起来保证"先历史后实时、顺序单调、不重不漏或明确报错"。

EventBus（内核线程内）

  • subscribe(task_id, after_sequence) 先注册队列，再回放历史 （kernel/events.py:70-86）。 注册必须在前，否则读库期间发布的事件会丢。
  • 回放和实时共用一个 watermark：历史里已交付的最大 sequence， 实时队列里 sequence <= watermark 的一律丢弃（:82-109）。 这就是"先回放后实时"的去重机制。
  • 历史按 list_events_page 分页（默认 128），旧仓储退化为 list_events 后切片； 页内出现 sequence <= watermark 直接 INTERNAL_ERROR（仓储返回乱序历史是 bug，不是降级点）， 每页之间 await asyncio.sleep(0) 让出循环，避免长历史独占内核 （kernel/events.py:55-68）。
  • publish 检查每个订阅队列，超过 max_event_buffer（默认 1000）就清空该队列并塞进一个 EventStreamOverflow 异常对象，附带"我最后交付到第几号"，调用方可以据此重放（:25-53）。 已经溢出的队列进入 _overflowed 集合，之后不再往里投递，避免反复清空。 溢出只影响这一个订阅者，不影响别的订阅者，也不影响任务本身。 宿主把 RuntimeOptions 传给内核构造函数，内核在构造 EventBus 时传入 page_size 和 queue_size，初始化后不再替换仓储或容量私有字段。
  • 看到终态事件就 return；close() 广播 None 哨兵，且哨兵排在所有已发布事件之后。

KernelHost（跨线程）

内核事件不能直接递到应用线程，所以是逐项拉取：

  • 应用侧的 async generator 每次 offline_next() 取不到就向内核线程 submit(stream.pull)， pull 在内核线程 anext 源生成器并做快照，然后交给等待方（hosting/kernel_host.py:100-113、:430-453）。
  • 关闭时 _drain_streams 把每个流剩余事件收进有界缓冲（max_event_buffer）， 缓冲没排空就溢出，同样带 watermark（hosting/kernel_host.py:115-138）。 这样"内核停了但客户端还没被唤醒"的窗口里的事件不丢。

流程 6：SDK 统一任务监听

只需要一个任务的最终结果时，两种 SDK 都提供 submit_and_wait(request, *, timeout_s=None)。 内部复用 submit_task，直接返回已终态快照，否则按任务 ID 回放历史并接续实时事件， 收到终态后关闭订阅并查询最终快照，不注册临时全局监听。快速完成、幂等重提和并发等待 沿用现有任务与事件语义，不修改内核或 UDS 协议。

流程 7：远程模式（UDS）

  • 一个请求一条连接：_request 打开 → 写一帧 → 读一帧 → 关闭 （remote.py:160-206）。 没有连接池，也没有请求超时；start() 只做一次 health。
  • 订阅是一条长连接：客户端发 subscribe_task_events，服务端持续写 {type:"event"}，历史放完后发 {type:"done"}。
  • 服务端检测客户端离开的方式很巧：reader.read(1) 与事件迭代器竞速， 读到东西（EOF 或任何字节）就取消订阅并清理（transport/server.py:272-282）。
  • 帧格式：NDJSON，单条上限 1 MiB（transport/wire.py:9-40）； 方法集 health / submit_task / get_task_status / cancel_task / list_skills / subscribe_task_events （transport/server.py:229-246）。
  • 服务端把 AgentRuntimeError 转成 {ok:false, error:{code,message,details}} （transport/server.py:210-221）， 客户端统一还原成 RemoteRuntimeError(code=...)（remote.py:243-257）。 代价：远程拿不到类型化异常，只能按 code 字符串分支——这是目前"两形态 API 一致"这条 承诺上唯一的破口。
  • 服务端自己也是 KernelHost 的宿主（transport/server.py:29-46）， 所以远程模式下内核同样独占线程；RemoteRuntime(options=...) 只用到本地 cancel_grace_s。

6. 横切机制（四条不能改坏的不变量）

6.1 状态唯一写入点：TaskStateStore.transition()

kernel/task_state.py:95-133。 一次转换固定四步，顺序不可变：

持该任务的 asyncio.Lock
  → 深拷贝活任务为快照，套用 changes
  → apply_transition(快照, 事件)   ← 快照与事件在一次仓储调用里原子写入
  → adopt_snapshot(活任务, 权威返回值)  ← 用仓储回填的值，不是用自己算的值
  → 最后才 events.publish(事件)

三个设计后果值得记住：

  • sequences[task_id] 只在这里 ++，所以事件序号单调（AGENTS.md 不变量 7）。
  • 权威值来自仓储：InMemory 做深拷贝（model_validate_json 往返）， SQLite 用 UPDATE 后重新读；因此活对象不会带着一个"内存觉得成功但库里没落"的状态。
  • 发布在写之后：订阅者永远不会看到一个库里还不存在的状态。

所有带 guard 的转换（execution_transition / try_succeed / request_cancel）共用同一把锁， 所以"取消"和"推进成功"是公平竞速，不存在已取消任务又被推进成功的窗口 （kernel/task_state.py:135-169）。 WorkflowExecutor 自身无状态，只做顺序和"恰好一次终态"映射。

进度上报是例外路径：每次 progress(v) 起一个后台 transition 协程，不阻塞技能； 步骤结束/失败/终态前用 drain_progress 收干，终态后靠 guard 拒绝， 关闭时靠 _shutting_down 丢弃（kernel/task_state.py:180-216）。

6.3 边界净化：bounded_snapshot

hosting/boundary.py:21-151。 所有跨线程数据都过它，两趟：先只计量不构建，再构建。

  • 计费口径是紧凑 JSON 的字节数（含 UTF-8 多字节与转义），默认 1 MiB / 深度 64，超限提前抛 SnapshotTooLarge，不先复制再检查。
  • 只用内建遍历（dict.__getitem__、str.__iter__、object.__getattribute__）， 因此外部对象的 __deepcopy__ / __iter__ / __repr__ 没有机会在内核线程上运行。
  • 允许的类型：JSON 标量、list/tuple/set/frozenset/dict、datetime（tzinfo 必须是裸 timezone）、以及 7 个规范模型（重建为基类，子类降级成普通容器）。引用环直接拒绝。
  • 异常也净化：丢弃外部 traceback 与异常链，按类名映射回 errors.py 里的类型， 非 AgentRuntimeError 统一压成 InternalError("Extension operation failed") （hosting/isolation.py:61-88）。

_Port.call 的完整路径值得看一眼（hosting/isolation.py:128-172）： 参数先快照 → 提交到该对象所属线程 → job.wait(port_timeout_s) → 结果 _unwrap（把 _Failure 还原成本地抛出的干净异常）。

超时这一步现在分成两种，因为它们的后果完全不同（:164-172）：

  • 还没开始跑（在 runner 队列里排队）→ job.cancel_if_queued() 在 runner 锁内把它摘掉并返回 True， 于是不毒化。毒化一个从未执行过的方法是没有根据的：它没有开始，也就不可能"正在提交"。
  • 已经开始或状态不明 → 照旧：poison=True 的端口永久拒绝后续操作，因为调用可能已经在跑。

这个判定之所以可信，是因为"开始"是在 runner 锁里写的（job._started = True， hosting/thread_runtime.py:206-209）， 而 cancel_if_queued 走的是同一把锁里的 _cancel(..., only_if_queued=True) （:257-273）—— 不是"看一眼标志位再决定"的竞态写法。整段理由就写在 _Port 的 docstring 里 （hosting/isolation.py:112-120）。 有了这层区分，port_timeout_s 设小了不再把纯排队中的仓储操作误判成永久毒化 （配对测试见 test_thread_binding_boundaries.py:59-113）。

写操作（write=True）超时后仍然不认账：它 shield 住真实完成的 job，一直等到真实结束或总 deadline， 因为"超时"不等于"没提交"（:154-163）。

6.4 请求 / 真实完成分离：LoopJob

hosting/thread_runtime.py:32-72。 LoopJob 的完成 Future 属于真实调用，等待方超时/取消都改不了它：

  • wait() 内部 wrap_future + shield，所以取消等待方不会取消远端工作。
  • cancel() 只是请求：还没开始的工作可以立刻取消；已开始且 cancellable=False （未声明 supports_cancel 的技能）直接忽略请求。
  • cancel_if_queued()（:61-62） 是 cancel() 的保守版：只在"确实还在排队"时才取消并返回 True，已经开始的一律返回 False 且不动它。 边界层用它把"排队超时"和"执行超时"分开处理，见 §6.3。
  • started() / done() / result() 让上层能区分"我放弃等待"和"它真的停了"。

这条是整个"不谎报停止"语义的地基。所有需要"必须等到真实结束"的地方都是同一个写法： while not done: await asyncio.shield(task)（吞掉取消继续等）， 出现在 hosting/isolation.py:155-163、 :452-457、 kernel/executor.py:281-287。 读代码时看到这种"怪写法"不要顺手改掉——那是防取消穿透的。

8. 配置：RuntimeOptions

10 个字段，全部构造期校验（拒绝 bool、非有限、非正数） （options.py:7-43）：

max_extension_threads 32 线程组上限：组数 + 1（校验线程） 绑定组合超出，构造期就 EXTENSION_CAPACITY_EXCEEDED

max_subscriptions 256 同时活动的事件订阅 订阅报错
max_snapshot_bytes 1 MiB 单个跨边界值 大输出/大参数直接 SNAPSHOT_TOO_LARGE
max_snapshot_depth 64 嵌套深度 深层结构被拒

cancel_grace_s 与 port_timeout_s 是两个语义上属于每个端口/每个技能的值，现在被做成全局， 这是配置模型里最别扭的地方（导航要 2s，TTS 只要 0.05s）。

adapters/cc_api/（真实硬件，第一个厂商接入包）

一个厂商一个目录，四个文件各司其职：contracts.py 放厂商 SDK 协议、driver.py 放请求与 回调分发、speech.py 放动作语义、platform.py 放装配与生命周期。内核与 SDK 不认得这个包， 只认它交出来的既有端口。

  • CcApiSpeechSkill 实现 audio.speak：resources={"speaker"}、permissions={"audio"}、 preconditions=set()、timeout_s=30、supports_cancel=True（speech.py:62-76）。 注意它故意不声明任何电量前置条件——AGENTS.md 不变量 5。
  • 端到端机制（值得单独读一遍，它是"回调式厂商 SDK 怎么变成 async 技能"的模板）： 技能 start() 只订阅驱动的 subscribe_finished / subscribe_failure，再 await driver.start() （speech.py:90-107）； 驱动 start() 才独占注册 SDK 回调（add_service("cc.api.work.finished") + set_disconnect_callback + notify("cc.api.work.subscribe")）并固定 owner 循环 （driver.py:98-122）。 订阅返回的是 detach 闭包，容量按 max_subscriptions 计 （driver.py:83-96）——这就是"多技能共用一个驱动不覆盖全局回调"的实现方式。 每次播报发 cc.api.work.start（skillCode="A000001"，speed/volume=50，独立 traceId）， 启动回调回填 workId，缺失即置 _broken 并抛 RobotResponseError （speech.py:308-321）； finished 在厂商线程触发，_on_finished 只 marshal 不回话 （driver.py:246-256）， 回到 owner 循环后按 workId 匹配才结算；finished 早于启动回调到达时缓存进 early_finished （上限 _MAX_EARLY_EVENTS = 128），超限直接 driver.invalidate 失败关闭 （speech.py:368-378）； 取消/超时/关闭走 _stop_work：先 shield 启动任务，启动被厂商拒绝（RobotRequestError）就直接返回—— 没有物理动作就无需停止；否则发 cc.api.work.ctrl {workCtrl:"stop"} 后继续等 finished， 整段套 5 秒 stop_timeout_s，超时/异常置 _broken 并抛 RobotStopError （speech.py:328-345）； 断连时驱动 _on_disconnect 通知所有失败订阅者，技能 _abort 给每个在途 future 注入 RobotConnectionError，此后实例拒绝再用 （driver.py:257-259、 speech.py:380-384）。
  • 驱动把厂商线程 → owner 循环这条桥抽出来了（_post / _deliver， driver.py:224-245）， 请求侧的容量与快照也在这里：control 标志分别用 max_control_calls 和 max_pending_calls 限额、入参与响应都过 bounded_snapshot、字段类型不符即 RobotResponseError （driver.py:124-155）。 但工作线程 → owner 循环的技能级 handoff（_execute_on_owner）还留在语音技能里 （speech.py:151-247）： 适配器只比较"当前循环是不是 _loop"，不同就用 concurrent.futures.Future 交接、deepcopy(params) 跨循环、call_soon_threadsafe 在 owner 循环建 task、asyncio.wrap_future 包回工作线程并转发取消。 也就是说与 hosting/isolation.py 无关的第二套线程桥仍然存在，只是缩短了一半； 等出现第二个回调型动作技能再合并，比现在凭一个样本抽基类靠谱。
  • 内核只等 cancel_grace_s（默认 0.2 秒），适配器自己的清理期限是 5 秒， 所以内核通常先判待对账，此时 speaker 资源保持隔离；应用必须先确认旧播报已停， 再建新连接和新实例（README.md:559-567）。
  • 不调用厂商 SDK 自己 cc_api 命名空间里带阻塞等待的 RobotClient；SDK 物理连接生命周期归应用， 驱动独占 finished 与 disconnect 回调，不允许别人在同一个 Api 实例上覆盖处理器。
  • CcApiPlatform 只做装配，不引入新概念：skills 用 MappingProxyType 交出只读映射， 没有真实状态源和对账器时 robot_state / reconciler 明确返回 None （platform.py:44-57）； 生命周期钉在 start() 所在循环，换循环调用直接 InvalidRequest（:58-63）； 启动只调技能 start()，由技能先领订阅令牌、再 await driver.start() 注册 SDK 回调， 这样第一个 finished 事件不会落在没人监听的时候；启动失败会连驱动一起关 （speech.py:97-107、 platform.py:73-81）； 关闭按 speech → driver，技能停止失败仍然释放驱动订阅 （platform.py:90-106）； asyncio.shield 包住 start/close 任务，所以等待者被取消不会重做清理（:65-71、 :83-89）。 工厂 create_cc_api_platform(api, *, stop_timeout_s=5.0, options=None, skill_thread_group=None) 的返回类型是 RobotPlatform 契约（:108-113）； skill_thread_group 非空时 skills 交出 ThreadBinding.group(技能, 组名) （:27-40），只改变宿主调用技能时的线程归属， start/close 仍在应用循环上直接操作原始技能对象。
  • SDK 侧唯一的消费入口是 RobotRuntime.from_platform(repository, platform, *, allowed_permissions=None, options=None) （sdk/embedded.py:49-63）： 它把 platform.skills / robot_state / reconciler 拆开喂给原构造函数，不新增状态、不启动平台。 平台生命周期仍由应用管——示例里的顺序是 platform.start() → runtime.start() → 提交任务 → runtime.close() → platform.close()（examples/cc_api_speech_demo.py:133-151）。

新增厂商包的做法

目标是只新增文件：adapters/<vendor>/ 里放 contracts.py（厂商 SDK 协议，若需要）、 driver.py（可选，多个技能共享连接时才需要）、动作技能文件、platform.py 与工厂； 再加一个 tests/test_<vendor>*.py，把文件名加进 .verify/sweep.py 的 FILES。 ports.py、kernel/、hosting/、sdk/ 与其他厂商包都不动——RobotPlatform 只聚合既有端口， 端口值可以带 ThreadBinding（skills / robot_state / reconciler 的标注都接受），绑定原样交给宿主， 也能像 CC 包那样用一个 skill_thread_group 参数替应用生成组绑定；不规定厂商必须有 request、callback 或 workId（ports.py:129-153）。 这条不是口头约定：test_contracts.py 里有一个非回调式的假厂商平台走同一个 from_platform 装配并通过同一份 check_robot_platform_contract （:26-59、 :61），它证明通用接口不需要任何 CC SDK 协议； :115 再覆盖 group / shared / dedicated / 裸对象四种绑定都原样穿过 from_platform。

  1. 实现 ports.py 的 Protocol，不继承、不注册，结构匹配即可；厂商私有协议留在自己的包里，不进 ports.py。

  4. 输入输出必须能表示成 JSON；大负载要评估 max_snapshot_bytes。
  5. 若内部有第三方线程的回调，一律 call_soon_threadsafe 转回自己的循环。
  6. 想清楚它该和谁共用 loop（thread_binding.py）： 会给不出停止信号、或者需要按时交付变化（状态源）的实现保持默认独占；只有确认不会同步阻塞 的轻量实现才合并成组。

11. 已知缺口

按"会不会咬人"排：

  1. 运维出口缺失。毒化与隔离永久，但没有诊断 API、没有人工解除入口，唯一办法是重启进程， 而"重启"在机器人上等于整机中断。这是第 7 节那张表的最后一列一直在说的代价。 线程绑定落地后多了一类同样缺失的观测："哪个对象挂在哪条线程 / 哪个组"没有公开查询接口， 目前只能从线程名（robot-extension-shared / -group-{name} / -dedicated-{i}）反推。
  2. cancel_grace_s / port_timeout_s 全局化。应当是端口/技能级声明。误配的后果已不像以前那样 绝对永久——纯排队超时会撤销且不再毒化（§6.3），但已开始的操作一超时就仍然永久毒化整个对象， 而"该给这个端口多少秒"依旧是全局一个数（导航要 2s，TTS 只要 0.05s）。
  3. 共享/分组是调用方的声明，运行时不校验它安不安全。把 RobotStateProvider 和可能阻塞的技能 分进同一组是允许的，出了事只表现为"急停标签晚到"，没有任何报错。README 写了禁止条款、 测试钉住了两种绑定的行为差别，但构造期无法区分"这个实现会阻塞"和"这个实现不会"， 所以这条只能靠约定。
  4. 远程模式错误降级为字符串 code，两形态在失败路径上不同构。
  5. 边界约束的报错不可读。越界值 → INTERNAL_ERROR("Extension returned an invalid snapshot")， 真实原因被刻意丢弃；SkillResult.output 声明是 dict[str, Any]，看起来什么都能放。
  6. 内核线程上的快照遍历：invoke() 与 pull() 的结果快照在内核循环执行，两趟遍历。 有界，但并发大时是毫秒级排队（hosting/kernel_host.py:400-401、 :110）。 共享线程只把它从"内核"挪到"那条组线程"，同组对象照样一起排队。
  7. 职责收拢已完成：SDK/Server 用 begin_close() 发起关闭；宿主按 core.stop → 排空已打开事件流 → core.close → 外部线程 → 内核线程 协调。 stop/close 分别共享真实结果，排空或停止错误不能跳过后续清理。
  8. 调度器：priority 已持久化但不排序，无并发上限、无抢占。 Agent 集成层（计划生成/重规划）、有限重试、结构化日志、其他真实能力适配 （导航/ROS 2）、CC API 结束原因解析与重启对账、云端管理平面均未做。
  9. GIL 与原生代码不设防（明确排除）。厂商扩展长时间持 GIL、进程退出钩子、 系统资源耗尽仍会影响整个进程；已运行的线程不能强杀。真要防这一层只有子进程。 共享线程也不改变这一点：同组对象本来就共担同一条线程上的同步阻塞。
